18  Adoptar TOML como formato preferente de configuración

EDR-00016 · General · accepted · 2026-09-15
Tags configuration toml yaml standards

19 Adoptar TOML como formato preferente de configuración

19.1 Contexto

IASI necesita un criterio común para los ficheros de configuración creados y controlados por sus propios artefactos. Entre los formatos candidatos, TOML y YAML (.yaml o .yml) ofrecen buena legibilidad humana y amplio soporte de herramientas.

Sin embargo, responden a objetivos diferentes. YAML es un lenguaje general de serialización capaz de representar estructuras complejas y ofrecer mecanismos avanzados. TOML está orientado específicamente a configuración y favorece una sintaxis más explícita, limitada y predecible.

Para IASI, un fichero de configuración debe ser fácil de leer y modificar por una persona, sencillo de procesar automáticamente y, sobre todo, difícil de interpretar de forma inesperada.

19.2 Decisión

IASI adopta TOML como formato preferente para la configuración propia del ecosistema.

Cuando IASI controle el formato de un fichero de configuración nuevo, se utilizará .toml por defecto.

YAML no queda prohibido. Se utilizará cuando sea impuesto por una herramienta, protocolo o ecosistema externo, o cuando exista una razón técnica concreta que haga más adecuada su capacidad para representar estructuras de datos complejas.

La decisión se aplica transversalmente a IASI y no está asociada a un artefacto, repositorio o subsistema concreto.

19.3 Rationale

La preferencia por TOML no se basa en que sea más expresivo que YAML, sino precisamente en que es deliberadamente menos expresivo para el dominio de configuración.

La menor cantidad de mecanismos sintácticos reduce el espacio de interpretaciones posibles y favorece configuraciones explícitas, estables y fáciles de validar.

Criterio TOML YAML
Orientación principal Configuración Serialización general de datos
Sintaxis Explícita y relativamente pequeña Flexible y muy expresiva
Indentación significativa No Sí
Tipos Explícitos y previsibles Más dependientes de reglas de interpretación
Estructuras jerárquicas Adecuadas, con mayor explicitud Muy naturales y compactas
Mecanismos avanzados Deliberadamente limitados Anchors, aliases, tags y otras construcciones
Riesgo de complejidad accidental Menor Mayor
Adecuación a configuración IASI Preferente Condicional

La restricción se considera una propiedad positiva: una configuración no necesita convertirse en un pequeño lenguaje para cumplir su función.

No elegimos TOML porque pueda expresar más que YAML, sino porque puede expresar menos y esas restricciones encajan mejor con lo que IASI necesita de una configuración.

19.4 Alternativas consideradas

Alternativa Ventajas Inconvenientes Decisión
TOML Explícito, predecible, orientado a configuración y con tipado claro Más verboso en estructuras profundamente jerárquicas Adoptada
YAML Muy legible en estructuras jerárquicas, compacto y ampliamente utilizado Mayor complejidad sintáctica y semántica; más formas de expresar lo mismo No como formato propio por defecto
JSON Universal, especificación pequeña y excelente interoperabilidad Poco cómodo para edición humana y sin comentarios estándar No adoptada para configuración humana

19.4.1 YAML como formato general

YAML sigue siendo apropiado cuando el problema consiste principalmente en describir estructuras de datos jerárquicas o cuando una tecnología externa lo establece como formato nativo.

Las extensiones .yaml y .yml representan el mismo formato y no constituyen alternativas diferentes dentro de esta decisión.

19.4.2 JSON como configuración

JSON es adecuado como formato de intercambio entre sistemas, pero no se adopta como formato preferente de configuración humana de IASI. La ausencia de comentarios estándar y su sintaxis más rígida lo hacen menos conveniente para ficheros mantenidos directamente por personas.

19.5 Consecuencias

Los nuevos formatos de configuración definidos por IASI deberán considerar TOML como primera opción.

Los artefactos existentes no deberán migrarse mecánicamente solo para uniformar extensiones. La migración tendrá sentido cuando IASI controle realmente el formato y el cambio aporte valor suficiente.

Cuando una herramienta externa requiera YAML, JSON u otro formato, IASI utilizará el formato requerido sin introducir conversiones artificiales únicamente para cumplir esta preferencia.

Las excepciones deberán responder a una necesidad técnica identificable y no simplemente a la costumbre de utilizar YAML para cualquier configuración.

La elección del formato de serialización tampoco convierte a TOML en el modelo de dominio. Cuando exista un modelo interno, TOML será una representación de entrada o persistencia de dicho modelo, no necesariamente su definición conceptual.

Configuración propia de IASI → TOML por defecto. Formato impuesto o necesidad específica → el formato que corresponda.
